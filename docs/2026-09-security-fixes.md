# 2026-09 安全修復總結

## 這輪做了什麼

從 CTO 健檢報告出發，依 P0→P1 順序，一次只修一塊、修完就驗證上線。

## 已修復（9 塊，全部 VERIFIED 上線）

### 1. release 鎖順序統一（migration 20260917）
- 問題：釋放訂單先鎖購物車再鎖商品，跟其他交易方向相反，高併發下可能互相等待。
- 修法：新增遷移把鎖序統一為「先商品後購物車」。
- 驗證：線上讀回函式定義命中，測試 19/19。

### 2. 推播函式上鎖（commit e7c0346）
- 問題：push-sale / push-price-drop 之前誰都能呼叫，還會吐錯誤細節。
- 修法：新增 `_shared/push_auth.ts`（排程密碼或管理員 JWT 二選一），限 POST，錯誤細節只進日誌不回給呼叫者。
- 驗證：匿名呼叫線上實測 401。
- 待辦：**排程密碼（PUSH_SCHEDULE_SECRET）要記得到 Supabase Edge Secrets 設定**，設好後 cron 才打得進去。

### 3. checkout 鎖順序統一（migration 20260918）
- 問題：結帳也是先鎖購物車，跟 purchase 相反方向。
- 修法：結帳改為先鎖商品再鎖購物車，跟全站一致。
- 驗證：線上讀回命中。

### 4. 狀態機前後台對齊（migration 20260919）
- 問題：前台有「已付款→完成」「退款拒絕→復活」按鈕，但資料庫沒開這兩條路，管理員按了一定失敗。
- 修法：DB 補開這兩條邊，其餘路徑跟罰則回補全部保留（只寬不緊）。
- 驗證：線上讀回兩條新邊命中；前台 `orderStatus.ts` 註解指向新版。
- 待辦：還沒拿真實訂單走完整流程（要動正式資料，等有真實訂單再驗）。

### 5. 關注人數批次查詢（migration 20260920）
- 問題：列表跟詳情頁每次都把全站關注表聚合一次，人一多列表先卡。
- 修法：新 RPC `product_follower_counts_by_ids(p_ids uuid[])` 只算傳入的商品；列表與詳情頁改用它，詳情頁順手拿掉整列全抓。
- 驗證：線上新函式命中。極限秒數未壓測（規模用不到，見下）。

### 6. 首頁輪詢瘦身
- 背景分頁停止三十秒輪詢，回到前景立即補抓；排程加隨機抖動避免整點同打。
- 關注數的即時推播：背景只記帳，回前景一次補齊。
- 罰則頻道事件只處理畫面上有的商品，訂閱只建一次。

### 7. 下單入口限流（commit 8496c19）
- 問題：腳本可以對 purchase 入口狂敲，鎖庫存不放手。
- 修法：`_shared/rate_limit.ts`，以身分（JWT user_id，匿名用 IP）計數，每分鐘十二次，超過回 429 並附等待秒數。
- 驗證：匿名呼叫 401；函式內限流驗完身分才計數。
- 已知特性：單實例記憶體計數，冷啟歸零；多實例時各自算各自的（目前規模可接受）。

### 8. 跨站白名單：推播兩支（commit 4b5987e + 005ae06）
- `_shared/cors.ts` 白名單：store-mvp.vercel.app、*.vercel.app 預覽、localhost 開發埠；非白名單不給 `Access-Control-Allow-Origin`。
- 過程修正：204 預檢不可帶 body，否則 Deno runtime 500（commit 005ae06）。
- 驗證：自家/陌生/無來源三情境線上實測全對。

### 9. 跨站白名單：admin + purchase（commit e50aaf5）
- 後台跟下單入口改用同一份白名單，全站函式跨站面收斂完畢。
- 驗證：四情境（陌生預檢、自家預檢、無來源、陌生實呼）線上實測全對。
